# ContainerBin v1.1.0

ContainerBin v1.1.0 is the first feature release after v1.0.0. It keeps the
existing Windows shim and command contracts while substantially expanding the
runtime catalog, state recovery, diagnostics, and supply-chain controls.

## Highlights

- Adds stable Node 22 and Node 24 profiles. The unversioned `node`, `npm`, and
  `npx` shims resolve through an atomic family default selected with `cb default`.
- Adds Go/gofmt, Rust/Cargo, uv/uvx, .NET 10 SDK, and Ruby/gem/bundle profiles.
- Extends `cb expose` to Go-installed binaries and adds provenance checks so
  `cb unexpose` cannot remove a merely similar hand-authored profile.
- Adds `cb add` for minimal reviewed stateless profiles.
- Adds explicit host mounts and isolated working-directory mode.
- Adds immutable image-ID locks for intentionally local images.
- Adds explicit, checksummed backup and restore for selected managed Docker
  volumes, in addition to registry and lockfile backup.
- Adds structured Docker invocation tracing, startup benchmarking guidance,
  proxy/air-gap documentation, and agent invocation guidance.
- Hardens release builds with deterministic archives, independent reproduction,
  provenance attestations, workflow linting, CodeQL, dependency review, and
  OpenSSF Scorecard checks.

## Upgrade from v1.0.0

1. Back up the directory containing `cb.exe`, `container-bin.toml`, and
   `container-bin.lock`.
2. Replace `cb.exe` with the v1.1.0 binary.
3. Run `cb setup` (or `cb install`). This migrates the default registry from
   schema 1 to schema 2, renames the stock Node 24 profiles to `node24`,
   `npm24`, and `npx24`, preserves the unversioned names as aliases, and appends
   the new default profiles.
4. Run `cb lock` or the appropriate `cb update` commands before invoking newly
   added profiles. An existing lockfile remains fail-closed until every selected
   image has an entry.
5. Run `cb doctor` and `cb self-test --release`.

The automatic schema migration deliberately refuses to guess when a v1
`node`, `npm`, or `npx` profile was customized. In that case it stops without
rewriting the registry and reports the manual action: rename the profile to an
explicit versioned name and add `default_family`, `default_version`, and
`default_alias` metadata before rerunning `cb install`.

Profiles generated by older `cb expose` versions do not have the new
`role = "exposed"` ownership marker. Recreate those profiles with
`cb uninstall TOOL` followed by `cb expose SOURCE TOOL` before using
`cb unexpose` on them.

## Compatibility notes

- Existing management commands and unversioned Node shim names remain valid.
- All runtime containers are Linux containers. Go, Rust, .NET, Ruby, and other
  native build outputs therefore target Linux unless the tool is explicitly
  configured for a Windows target.
- New default profiles add new container images but do not pull them during
  registry migration. Locking and normal Docker image availability rules still
  apply.
- `cb backup --state` includes only explicitly named, consistently labeled
  ContainerBin volumes and requires the pinned helper image to be present.
- The release remains Windows amd64 only. Windows ARM64 is not claimed or
  packaged in v1.1.0.

## Verification

Download `cb.exe`, the ZIP archive, and `SHA256SUMS` from the GitHub release.
Compare the SHA-256 digest and verify the GitHub build-provenance attestation as
described in the README. The release workflow produces the binary and archive
twice on independent runners and requires them to be byte-identical before it
creates the draft release.
