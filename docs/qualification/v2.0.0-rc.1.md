## Pipx blocker and separate source-built follow-up

The published candidate failed the additional managed-app exposure cell:
`pipx install cowsay==6.1` installed the package, then its wrapper rejected a
launcher-cache `bin/python3.13 -> python` alias resolving to the exact approved
image interpreter. The launcher allowlist accepted only `python`, unlike the
application/shared venv alias allowlists. Filesystem traversal order can expose
the alias before its target has been copied into the managed volume.

The focused fix accepts only `python`, `python3` and the exact approved
interpreter's versioned name in that same five-component launcher location.
The exact resolved external target check remains unchanged. Regression tests
cover direct/chained aliases, creation order, wrong names/locations and foreign
external targets.

A **source-built follow-up**, not the published RC, used injected version
`v2.0.0-qualification.pipx1` and Windows/amd64 SHA-256
`2c6e526483a8bd284b01c818c8a81053138b0c046010e104d58cec346073e379`.
With a fresh private default registry, it recovered the failed RC test store,
exposed/invoked the existing cowsay app and removed it. A fresh store then
passed pinned install, explicit exposure/invocation, unexpose, store-wide
exposure/invocation and final unexpose/uninstall. Only the newly-created,
ownership-verified disposable store was removed; no pre-existing store was
used or deleted. Updating an existing embedded wrapper requires an explicit
registry profile refresh as documented in README; custom/signed registries
are not silently rewritten.

The follow-up also passed all 15 embedded Python tests, formatting/vet/full Go
race tests, release-style version injection and a native Windows release
self-test with 15 passed, zero failed and zero skipped. Native Windows x64/ARM64
unit suites and independent bundle reproduction remain CI gates for its PR.
